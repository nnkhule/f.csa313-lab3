## SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл |
|---|---|---|---|
| Performance | /cart/add latency | p(95) < 50мс | 20 VU, 1 мин |
| Reliability | /pay error rate | rate < 0.08 (8%) | 20 VU, 1 мин |
| Availability | Бүх хүсэлтийн амжилтын хувь (checks) | rate > 0.90 (90%) | 2 мин, дунд нь 10с зогсолттой |

**Босго сонгосон үндэслэл:** Сервер `/pay` дээр ~5% алдаа зориуд суулгасан тул 8% гэдэг нь бодит суурь алдаанаас дээгүүр, боловч том биш бодитой хязгаар.

**Error budget (цагаар):** 2 минутын 10% = 12 секунд "эвдрэх эрх".


/cart/add нь энгийн синхрон JSON хариу тул localhost дээр анхны туршилтад p95=1.42мс байсан. Анхны p(95)<200 threshold хэт сул байсан тул p(95)<50-д бууруулсан — энэ нь бодит гүйцэтгэлээс дээгүүр зай үлдээх боловч удаашрал үүсвэл шалгах чадвартай.


## Chaos туршилт (Алхам 5)

Гаралт: [results/chaos.txt](results/chaos.txt)
Зураг: [results/chaos_fix.png](results/chaos_fix.png)

**Тестийн нөхцөл:** 20 VU, 2 минутын турш. Тест дунд орчимд (~секунд 33-37)
сервер `Ctrl+C`-ээр зогсоож, ~10 секунд хүлээгээд `node server.js`-ээр
дахин асаасан.

**Threshold-ийн үр дүн:**

| Threshold | Утга | Үр дүн |
|---|---|---|
| checks (Availability) `rate>0.90` | 91.23% | ✓ PASS (нарийн зөрүүтэй) |
| http_req_failed{pay} (Reliability) `rate<0.08` | 11.78% | ✗ FAIL |
| http_req_duration{cart} `p(95)<50` | 960.58µs | ✓ PASS |

**Endpoint тус бүрийн амжилтгүй хувь:**
- /cart/add: 134/1875 = 7.15% амжилтгүй
- /report: 138/1875 = 7.36% амжилтгүй
- /pay: 221/1875 = 11.78% амжилтгүй (үүнээс ~5% нь серверийн зориудаар
  суулгасан суурь алдаа, үлдсэн ~6.78% нь chaos-ийн улмаас)

**Бодит availability = амжилттай хүсэлт / нийт хүсэлт = 5132 / 5625 = 91.23%**
(k6-ийн `checks` метрик яг энэ тооцоог өгдөг, учир нь хүсэлт бүрд нэг
`status===200` check хийгддэг.)

**Error budget харьцуулалт:**

Алхам 3-т 2 минутын цонхны 10% = 12 секундийг "эвдрэх эрх" гэж цагаар
тооцсон. Хүсэлтийн хурд (нийт 5625 хүсэлт / 121.2с ≈ 46.4 хүсэлт/с)-аар
бодит амжилтгүй хүсэлтийг "экв. секунд"-т хөрвүүлбэл:

    493 амжилтгүй хүсэлт / 46.4 хүсэлт/с ≈ 10.6 секунд

Энэ нь 10 секундийн бодит зогсолттой ойролцоо тохирч, 12 секундийн
budget-т **багтсан** байна. Тиймээс availability threshold нарийн зөрүүтэй
ч PASS болсон нь тохиолдлын зүйл биш — зогсолтын хугацаа budget-аас бага
байсан учраас юм.

Гэхдээ энэ тохирол санамсаргүй ойрхон гарсан бөгөөд алдааны зөрүү бага.
Хэрэв зогсолт бодит цагаар 12 секундээс бага байсан ч, унасан үед хүсэлт
connection-refused-ээр **шууд** (`/report`-ын хэвийн 200-400мс хүлээлтгүйгээр)
буцдаг тул хэвийн ажиллаж байх үеийнхээс илүү олон хүсэлт нэг секундэд
"иддэг". Энэ нь цагаар тооцсон budget ба хүсэлтээр тооцсон budget яагаад
ерөнхийдөө ижил биш байдгийг тайлбарлана — манай тохиолдолд эдгээр хоёр
тоо санамсаргүй ойрхон гарсан.

**Reliability threshold яагаад мөн FAIL болсон вэ:**

Сервер унасан үед `/pay` рүү илгээсэн хүсэлт бүр connection-refused-оор
амжилтгүй болдог тул серверийн зориудаар суулгасан ~5% суурь алдаан дээр
chaos-ийн улмаас нэмэлт алдаа нэмэгдэж, нийт rate 11.78% болж 8% босгыг
давсан. Нэг эвдрэл (сервер унах) availability болон reliability гэсэн
**хоёр өөр SLO-г зэрэг зөрчсөн**, учир нь хоёулаа адилхан "хүсэлт
амжилттай эсэх"-д тулгуурладаг.

**Availability ба reliability SLI-г тусгаарлах арга:** Availability-г
зөвхөн "сервер холбогдож байна уу" (жишээ нь health-check endpoint эсвэл
connection error) дээр үндэслэж, харин reliability-г зөвхөн серверийн
**200 статустай хариулсан** хүсэлтүүд дундах бизнес-логикийн алдаа
(жишээ нь `/pay`-ийн 500 gateway timeout)-аар хэмжвэл, серверийн бүрэн
унал нь зөвхөн availability-д тусгагдаж, reliability тоог гуйвуулахгүй.

“Хүсэлтээр хөрвүүлсэн эквивалент алдагдал 10.6 секунд гарсан нь 12 секундийн error budget-тэй ойролцоо байна. Гэхдээ энэ нь бодит downtime-ийн секунд биш тул error budget-ийг баталгаажуулах шууд хэмжүүр гэж үзэхгүй.”



## Threshold зориуд эвдсэн (Алхам 6)

Гаралт: [results/fail.txt](results/fail.txt)

`/report`-ын threshold-ыг `p(95)<450` → `p(95)<100` болгож чангаллаа.
Сервер `/report`-д 200-400мс хооронд санамсаргүй хугацаагаар хариулдаг
тул (server.js-д `sleep(200 + Math.random()*200)` гэж заасан) p95 нь
энэ хязгаараас доогуур гарах боломжгүй — тиймээс энэ threshold ямар ч
машин дээр найдвартай FAIL болно.

**FAIL мөр: exit=99**


**Exit code:** [99, `"exit=$LASTEXITCODE"`-аас]

**`/cart/add`-ыг `p(95)<50` болгоход яагаад PASS хэвээр үлдэх вэ:**
`/cart/add` нь `sleep()` ашигладаггүй синхрон endpoint тул бодит p95 нь
1.05мс орчим байдаг — энэ нь `/report`-ын дор хаяж 200мс-ийн доод
хязгаараас 190 дахин бага. Тиймээс `p(95)<50` threshold ч давамгайлж
PASS үлдэнэ, учир нь 50мс нь бодит утга (1.05мс)-аас хэд дахин өндөр
хэвээр байна. Харин `/report`-ын хувьд ямар ч тохиргоотой ч түүний
доод хязгаар (200мс) 100мс-ээс өндөр байдаг тул FAIL болохоос өөр
аргагүй.

**Яагаад энэ чухал вэ (CI-тай холбоотой):** k6 threshold FAIL болоход
k6 0-ээс өөр exit code буцаадаг. CI pipeline (жишээ нь GitHub Actions,
GitLab CI) build-ийн амжилт/амжилтгүйг яг энэ exit code-оор шийддэг —
0 бол алхам амжилттай, 0 биш бол алхам зогсоно. Иймд threshold бол
зөвхөн тайлангийн тоо биш, автоматжуулсан шалгалтын **гарц (gate)**
болж ажилладаг.




## Дүгнэлт

Энэхүү лабораторийн ажлаар чанарын гурван сценариог хэмжигдэхүйц SLO болгон хувиргаж, k6 threshold ашиглан автомат шалгалт хийлээ. Performance сценариогийн хувьд `/cart/add` endpoint-ийн p95 latency-г 50 мс-ээс бага байхаар тодорхойлж, туршилтаар энэ босгыг хангаж байгааг баталсан. Reliability сценариод `/pay` endpoint-ийн алдааны түвшинг 8%-иас бага байхаар тогтоосон боловч chaos туршилтын үед 11.78% болж threshold FAIL болсон. Availability сценариод серверийг ойролцоогоор 10 секунд зогсоож дахин ажиллуулахад нийт хүсэлтийн 91.23% нь амжилттай боловсруулагдсан тул 90%-ийн босгыг давж PASS болсон. Chaos туршилт нь availability сценариод тодорхойлсон хэмжүүрийг бодитоор шалгах боломж олгож, серверийн түр зогсолт хэрэглэгчийн хүсэлтэд шууд нөлөөлж байгааг харуулсан. Гэхдээ availability-г зөвхөн амжилттай хүсэлтийн хувиар хэмжихэд серверийн downtime болон хүсэлтийн давтамжийн ялгаа нөлөөлж болохыг туршилтын явцад ажигласан. Мөн нэг серверийн crash нь availability болон reliability-ийн хэмжүүрт зэрэг нөлөөлж болох тул эдгээр SLI-ийг тусгаарлан тодорхойлох шаардлагатайг ойлгосон. Threshold-ийг зориудаар зөрчүүлсэн туршилтаар `/report` endpoint-ийн p95 босгыг 450 мс-ээс 100 мс болгон чангаруулахад k6 `exit=99` буцааж, threshold нь CI pipeline-д автомат quality gate болж ажиллаж болохыг баталсан. Иймээс чанарын ерөнхий шаардлагыг хэмжигдэхүйц SLI, SLO болгон задлан тодорхойлж, тэдгээрийг k6 threshold-тэй холбох нь системийн гүйцэтгэл, найдвартай байдал болон availability-г автомат байдлаар шалгах боломж олгодог.
